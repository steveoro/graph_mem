# AGENTS.md

GraphMem is a Rails 8.1 app (Ruby 3.4.1, MariaDB 11.8+) that serves a
graph-based agent memory over MCP, plus a REST API and an operator web UI.
This file is the one set of rules for every coding agent in this repo (Claude
Code reads it through `CLAUDE.md`'s `@AGENTS.md` import).

## graph_mem memory (MCP)

This project uses the graph_mem MCP server: a shared knowledge graph of what
earlier sessions learned (conventions, preferences, where things live, verified fixes).
Use the `graph-mem-mcp-toolset` skill:
- at the start of a task, to load the project's conventions and the user's preferences;
- before deciding a convention (version bump, changelog or docs style, tests, naming,
  config location, release steps) or first editing a file or component;
- before the final reply, to save corrections, preferences, locations and verified fixes.
Without the skill: call `search` before deciding, and `graph_write` before the final reply.

## Developing GraphMem (editing this codebase)

### Commands

Ruby is pinned to its own RVM gemset (see "Ruby commands (RVM)" below), so every
command runs as `source "$HOME/.rvm/scripts/rvm" && rvm use ruby-3.4.1@graph_mem && bundle exec <command>`.

- Lint: `bundle exec rubocop` (autofix: `-a`)
- All tests: `bundle exec rspec` (needs a real MariaDB 11.8+; specs use real instances, not doubles)
- Single spec: `bundle exec rspec spec/services/graph_write_service_spec.rb[:LINE]`
- Dev stack: `bin/dev` (Procfile.dev: rails server, tailwind watcher, `bin/jobs` for Solid Queue)
- MCP over HTTP on port 3030: `bin/mcp`; over stdio: `bin/mcp_stdio_runner.rb`
- Docs: `docs/development.md` (setup), `docs/architecture.md`, `docs/troubleshooting.md`,
  `docs/operator/` (operator UI). Tool reference: `docs/mcp_tools.md`.

### Database gotchas

- Schema format is SQL (`db/structure.sql`), not `schema.rb`. MariaDB older than 11.8 silently drops the `vector(768)` columns/indexes from the dump. After any migration, `git diff db/structure.sql` and never commit disappearing `vector(768)` lines or pragma churn (`@OLD_NOTE_VERBOSITY` turning into `@OLD_SQL_NOTES`).
- Embeddings are 768-dim vectors generated by an external Ollama instance (`EmbeddingService`).

### Architecture

Layers: MCP tools / REST controllers → services + strategies → ActiveRecord models → MariaDB.

- **Data model**: `MemoryEntity` (typed nodes, with embeddings), `MemoryObservation` (facts attached to an entity), `MemoryRelation` (typed edges). `Project` entities are context roots; `part_of` is an ownership edge, so an entity has at most one `part_of` parent. Relation semantics live in `RelationSemantics` / `GraphVocabulary`.
- **MCP layer** (`app/tools`, `app/prompts`, `app/resources`): tools inherit `ApplicationTool` (the `arguments` DSL of `GraphMem::McpSchema::ToolApi`, in `lib/graph_mem/mcp_schema/`). `McpToolRegistry` loads the 22 tool classes. The protocol is served by the official MCP Ruby SDK (`mcp` gem, pinned to 1.8.1) through `lib/graph_mem/official_mcp/`, which wraps the tools, prompts and resources into one `MCP::Server` per profile. Three HTTP profiles: `/mcp` (default, 12 tools), `/mcp/readonly` (9), `/mcp/maintenance` (all 22); DNS-rebinding protection (`Host`/`Origin` checks) stays on. Errors go through the `ToolError` envelope (`category`, `retriable`, `next_move`, `message`). See `docs/mcp_tools.md`.
- **Per-agent context**: the active project context is persisted in the DB (`AgentContext`), keyed by the `X-MCP-Client` header. Names resolve in this order: context project, then global, then a single foreign-scope candidate, else `AmbiguousReference`. Destructive ops by bare name can hit another project's entity, so use `entity_id`.
- **Writes** go through `GraphWriteService` / `GraphEditService` / `GraphDeleteService` (`graph_write`, `graph_edit`, `graph_delete` are the consolidated mutation tools; see `docs/mcp_toolset_consolidation.md`). Mutations cooperatively pause dream-state compaction.
- **Search** (`app/strategies`): hybrid, vector (MariaDB MHNSW), entity and temporal strategies, plus relevance/trust ranking services.
- **Background jobs** (`app/jobs`, Solid Queue): dream-state compaction (auto-parents orphans, auto-merges near-identical same-type entities, queues the rest as maintenance review rows), garbage collection, embedding backfill/maintenance, DB backup, exports, project scans. Compaction behavior: `docs/dream_state.md`.
- **Project scans** (`ProjectScanner`, `ProjectScanValidator`, `RailsAstExtractor`, `GraphifyImporter`): treat source files as truth, reconcile the graph, then run a batched, resumable validation pass. Scan-sourced observations (`source` starting with `project_scan:`) can be auto-moved or obsoleted. Manual ones are only queued as `scan_review` maintenance rows, never silently deleted.
- **Operator UI**: `app/controllers/operator`, Stimulus/importmap JS, Tailwind, ActionCable progress channels (`OperationProgress`). Docs: `docs/operator/`. REST API: `app/controllers/api/v1` with Swagger via rswag (`swagger/`).
- Specs mirror `app/` under `spec/`. Rake tasks are in `lib/tasks` (embeddings, graphify, rails_ast, structure_dump, etc.).

### Coding rules

- **Schema first**: DB schema is the primary source of truth for data structure.
- **Know your context**: Verify project folder and development environment, runtime target, and containers before running commands.
  Example: most workspaces include more than one project root, each with its own dev stack and languages. Focus on the target project, look for relevant files in the project root that might include target versions of the dev stack in use. (E.g: `.versions.conf`, `.ruby-version`, `docker-compose.yml`, `Gemfile`, `package.json`, `.rvmrc`, ...)
- **Keep it simple**: Prefer straightforward solutions and small, testable units.
- **Test like production**: Real instances over doubles; randomize factories; no fake data in dev/prod.
- **Don't sprawl**: Touch only code relevant to the task; avoid architecture shifts unless asked.
- **Refactor early**: Split files >500 lines or functions >60 lines.
- **Evolve, don't fork**: Fix within current patterns before introducing new tech; remove old impls if replaced.
- **Document**: Record critical changes; remove one-off helpers once used.
- **Document public APIs**: When adding or editing classes, describe basic
  usage and the expected parameter/return types on public methods. Prefer
  concise YARD-style comments for Ruby.

### Ruby commands (RVM)

This project pins its own Ruby **and** its own gemset, which are not the shell default, so a
bare `bundle`/`rspec` runs against the wrong Ruby.

#### The rule

Never run `bundle`, `rails`, `rake`, `rspec`, `rubocop`, `gem` or a generator from a bare
shell. Select the gemset first, in the same command:

```bash
source "$HOME/.rvm/scripts/rvm" && rvm use ruby-3.4.1@graph_mem && bundle exec <command>
```

`source` is required: `rvm` is a shell function, absent from non-interactive shells.
`.versions.conf` (`ruby=` plus `ruby-gemset=`) is the source of truth if the pin changes.

#### Do not rely on the per-directory auto-switch

RVM's project switch is a `cd` hook installed by the *interactive* shell profile. Scripted and
agent shells are non-interactive, so it may apply to one command and silently not to the next.
An explicit `rvm use` is mandatory even when a previous command in the same shell happened to
pick up the right Ruby.

#### A wrong-Ruby run looks like a broken bundle

It fails with `Bundler::GemNotFound` and a "Could not find ..." list naming most of the
lockfile. That means the gemset was not selected, not that the bundle is broken:

- Do **not** run `bundle install` or install gems to make it pass.
- Re-run with `rvm use`, and add `ruby -v` to confirm the version before trusting a pass or a
  failure.
- `Warning! PATH is not properly set up` from `rvm use` is harmless; the gemset is selected.

### Git safety

When deleting untracked files, if in doubt first track them with `git add`, then delete them. This keeps the deletion in the staging area and makes the operation reversible anytime.
